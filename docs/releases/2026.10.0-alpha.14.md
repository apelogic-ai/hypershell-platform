# Steward platform 2026.10.0-alpha.14

A pre-release of the Steward platform BOM that moves Steward to **0.3.16**.
steward-run 0.8.1, github-oidc-exchange 0.7.5 and mcp-gw 0.5.7 are unchanged.
It is an alpha: the governed profile, which runs agents, is not in it yet.

Read the upgrade notes first. Steward 0.3.16 changes the format of the agent
catalog, and an install that runs agents must upgrade in one coordinated step.

## Upgrade notes

Steward owns this procedure:
[Upgrade and rollback](https://github.com/apelogic-ai/steward/blob/v0.3.16/CHANGELOG.md#upgrade-and-rollback)
in its changelog and the
[execution-binding upgrade procedure](https://github.com/apelogic-ai/steward/blob/v0.3.16/docs/installation/upgrade-execution-bindings.md).
What follows is what it means for an install of this platform.

- **One coordinated step.** Pause Task submission and Workflow publication.
  Update the agent catalog to `steward.execution-bindings/v2`. Roll the Steward
  chart and all of its images together. Resume only when no old apiserver or
  controller pod remains. Changing only the images, or only the catalog, leaves
  one side unable to start: the 0.3.16 chart schema and API server refuse a v1
  catalog.
- **Agent catalog v2.** Every agent in the catalog must declare the model
  providers it supports, in `models.providers`. Keep every other field of each
  agent unchanged.
- **Preflight input.** If you use Steward's deployment preflight, its input
  must add `execution.binding.modelProviders`, and that list must cover every
  provider named in the capability catalog's `models`.
- **No downgrade once a Task exists.** After Steward 0.3.16 has created any
  Task, do not go back to 0.3.15: the earlier binaries cannot read that Task.
  Before the first such Task, you can restore the previous binaries and the
  exact v1 catalog together, while submission stays paused.
- **Migrations 0069 and 0070 are additive.** They run when the new apiserver
  and controller start and stay in place on rollback. 0070 appends a narrower
  revision to each Envelope template whose retired automatic-provision
  threshold was stricter than its limits; keep those revisions. Back up the
  Steward database before upgrading.
- **Agent images.** Full execution logging now needs `setsid`, `head` and
  `tail` in the agent image, and Linux procfs at `/proc`. The Codex reference
  runtime pinned here (`0.140.0-steward-0.3.16`) has them, and adds `rg`, `jq`,
  `fd` and `tree`.
- **Inference route timeout.** Still required on a governed edge:
  [#63](https://github.com/apelogic-ai/hypershell-platform/issues/63).

**For the core, task-auth and browser-admin profiles of this BOM** the
coordinated step needs no manual catalog work:

- These profiles run no agent and admit no Task. The generator sets no agent
  catalog, so the Steward chart's own default applies, and that default moves
  to the v2 format with the chart. Nothing in the platform values changes.
- There is no Task submission or Workflow publication to pause, and no
  preflight input to change.
- Rolling back to alpha.13 needs no database restore, because no Task is
  created. Apply the 0.3.15 chart and full image set together. On
  browser-admin, migration 0070 may have added template revisions: keep them.

**For an install that runs agents** (outside this BOM, with its own Steward
values): the catalog, the preflight input and the pause are yours to carry
out, exactly as Steward's procedure says. This repository cannot generate
them yet; see [What it does not do yet](#what-it-does-not-do-yet).

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

### What changed in Steward

[Release notes](https://github.com/apelogic-ai/steward/releases/tag/v0.3.16)
and [changelog](https://github.com/apelogic-ai/steward/blob/v0.3.16/CHANGELOG.md).
In short:

- **Agents and models are configured by the deployment.** The agent catalog
  declares each agent's model providers; the browser's model picker and Task
  planning use it, and an agent and model that do not go together are refused
  before anything is reserved.
- **Live execution logs.** With full execution logging, Steward stores bounded
  output while a Task runs and keeps the final output.
- **Requests at or below the limit are admitted.** A Task may ask for less
  than its Envelope allows, for example a smaller scratch size.
- **One boundary for Envelope templates.** Requests within a template's limits
  provision automatically; requests above them go to an administrator. The
  separate automatic-provision threshold is retired (migration 0070).
- **Workspaces by name.** A Git workspace may name an admitted repository as
  `owner/repository` and a plain branch or tag; Steward still records the
  exact commit.
- **Codex reference runtime.** Adds `rg`, `jq`, `fd` and `tree`.

**Chart values.** The 0.3.16 chart changes one thing: the agent catalog
(`config.apiserver.executionBindings`) must be `steward.execution-bindings/v2`,
with `models.providers` required for each agent. The generated Steward values
change only in image tags and digests. The rendered install changes its agent
catalog ConfigMap, which is content-addressed, from the empty v1 catalog to the
empty v2 catalog, so the apiserver rolls once.

## Changes in this repository besides versions

- **Repository URL in generated output.** The repository was renamed to
  `hypershell-platform`. The generator now emits the new URL as the
  `GitRepository` source of `charts/steward-edge` (task-auth Flux output) and
  as the Git entry of the mirror list. The `GitRepository` is still named
  `steward-platform`; no installed resource name, chart name, namespace,
  values key or product name changed. The old URL keeps redirecting.
- **Chart metadata.** `home` in the four charts of this repository points at
  the new URL. `charts/steward-edge` therefore differs from its alpha.13
  content in that one line; the Flux output installs it from this version's
  tag.
- **Schema identifiers stay.** The `$id` of the three published v1 schemas
  keeps the old repository name. It is an identifier that consumers may have
  registered or cached, the old URL still resolves, and nothing in this
  repository resolves a schema through it. It will change with a v2 of the
  schemas.
- **Agent catalog check.** The generator test now checks, for every
  environment, that the rendered Steward chart carries an empty agent catalog
  in the v2 format, in staged mode.

## Upgrading from 2026.10.0-alpha.13

- **Platform values** from alpha.13 validate unchanged. Regenerating with this
  BOM changes:
  - the Steward chart digest and the Steward image tags and digests;
  - the `platformVersion` and the `GitRepository` tag;
  - for task-auth Flux output, the `GitRepository` URL of `steward-edge`
    (the new repository name).
- **Back up the Steward database**, then apply with
  `helmfile --environment <env> --kube-context <context> sync`, or let Flux
  reconcile the regenerated objects. Deploy the Steward chart and images as
  one release unit.
- **Git mirror** (task-auth with `registry.gitSources`): mirror this
  repository under its new name, with the `2026.10.0-alpha.14` tag. A
  `gitSources.repositories` entry keyed by the old URL no longer matches;
  change its key to `https://github.com/apelogic-ai/hypershell-platform`. With
  `gitSources.prefix`, the mirror is read at the path of the new name. See
  [registry mirroring](../registry-mirroring.md).
- **Registry mirror and built mode:** copy or rebuild the new Steward
  artifacts. An alpha.13 lock is refused.
- **Callers:** none change.
- **Installs that run agents:** follow [Upgrade notes](#upgrade-notes) above.
  The SPIRE settings from the alpha.10 notes still apply.
- **Rolling back** to alpha.13: see [Upgrade notes](#upgrade-notes).

## What it does not do yet

Unchanged from [alpha.10](2026.10.0-alpha.10.md#what-it-does-not-do-yet), and, for
Steward 0.3.16's new requirements:

- The platform values have no field for the agent catalog, and the generator
  cannot emit one: agents belong to governed mode
  ([#3](https://github.com/apelogic-ai/hypershell-platform/issues/3)). The
  model providers a deployment offers are already in the platform values, as
  `administration.capabilityCatalog.models[].provider`; a generated catalog
  will have to name, per agent, the ones that agent supports.
- This repository does not produce Steward's deployment-preflight input.
- No test here runs an agent, so the agent image requirements of full
  execution logging are not exercised.
