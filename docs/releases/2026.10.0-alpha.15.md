# Steward platform 2026.10.0-alpha.15

A pre-release of the Steward platform BOM that moves Steward to **0.3.19**
(from 0.3.17, including 0.3.18) and mcp-gw to **0.6.0** (from 0.5.7).
steward-run 0.8.1, github-oidc-exchange 0.7.5 and every third-party
dependency are unchanged. It remains an alpha: the governed profile, which
runs agents and would install mcp-gw, is not implemented yet.

Read the upgrade notes first. Steward 0.3.18 adds migration 0071 and changes
the governed provider and Task-evidence contracts. MCP-GW 0.6.0 makes exact
Task tool approvals the default and adds an opt-in Jira provider. Steward
0.3.19 adds no migration or configuration change over 0.3.18.

## Upgrade notes

Steward owns its procedure: the *Upgrade and rollback* sections for
[0.3.19](https://github.com/apelogic-ai/steward/blob/v0.3.19/CHANGELOG.md#upgrade-and-rollback)
and
[0.3.18](https://github.com/apelogic-ai/steward/blob/v0.3.19/CHANGELOG.md#upgrade-and-rollback-1),
and the
[installation guide](https://github.com/apelogic-ai/steward/blob/v0.3.19/docs/installation/installation-guide.md).
MCP-GW owns its
[0.6.0 upgrade notes](https://github.com/apelogic-ai/mcp-gw/blob/v0.6.0/CHANGELOG.md#upgrade-notes).
What follows is what those releases mean for a combined installation.

- **Back up Steward's database.** Apply additive migration 0071 before the
  new Steward processes serve. It adds an optional preferred-Envelope digest
  to immutable browser Task versions; existing rows remain unchanged.
- **Deploy Steward as one release unit.** Roll the 0.3.19 chart and every
  Steward image together. 0.3.19 adds no migration or required configuration
  beyond 0.3.18.
- **Mint before provider display names.** In a governed installation, replace
  every old Mint pod before adding capability-catalog `displayName` fields.
  Older Mint replicas refuse those fields.
- **Jira is opt-in.** The BOM pin does not enable Jira and this repository
  still generates no mcp-gw values. Enabling Jira requires MCP-GW 0.6.0, a
  dedicated Atlassian OAuth app, the exact callback route, an existing Secret,
  the shared OAuth migrations, and the exact Jira wrapper under Steward's
  `connectionsBridge.providerOrigins`.
- **Use the read-only Jira preset.** `jira-read-only` exposes current-user,
  issue-search and issue-get and requests only `read:jira-user`,
  `read:jira-work` and `offline_access`. Do not enable the full preset merely
  because 0.6.0 contains it; its known custom-app access limitation remains.
- **Temporary Jira session setting.** Until MCP-GW 0.6.1, every enabled Jira
  wrapper must set `sessions.maxPerPrincipal: 32`. The wrapper reads this
  value; it prevents the 0.6.0 per-principal default from rejecting the
  intended concurrent Jira sessions. It has no effect while Jira is absent.
- **Exact Task tool approvals.** MCP-GW 0.6.0 refuses missing, malformed,
  old-version or unknown Task approvals by default. The supported Steward
  issuer sends the v3 authority format. Keep
  `taskToolAuthorization.allowLegacyUnscopedTaskTokens: false`; the true value
  is an unsafe one-release bridge only for a custom legacy issuer.
- **Route wrappers, not raw backends.** Task traffic for GitHub must continue
  through `github-wrapper`; db-mcp must use its opt-in wrapper before Task
  tokens can reach it. An arbitrary direct backend must enforce the same
  approval contract itself.
- **Existing providers keep their credentials.** MCP-GW 0.6.0 requires no
  reconnect, provider reauthorization or Secret-format change for existing
  Google Workspace or GitHub connections.

For an enabled Jira wrapper, the release-specific overlay includes this
setting alongside the complete values defined by MCP-GW's
[Jira example](https://github.com/apelogic-ai/mcp-gw/blob/v0.6.0/deploy/k8s/examples/values-jira.example.yaml):

```yaml
wrappers:
  - name: jira
    enabled: true
    catalog:
      preset: jira-read-only
    sessions:
      maxPerPrincipal: 32
```

The snippet is not a complete Jira installation and does not create any
credential. Keep literal OAuth values and encryption keys out of Helm values.

### Rollback

- Keep migration 0071 and its historical rows when rolling Steward back.
- Before rolling Steward below 0.3.18, stop Task submission and prove that no
  stored Task evidence contains `taskRuntimeMinutesLimit`. Remove every
  capability-catalog `displayName`, disable Jira and remove its tool/catalog
  entries, and remove provider-specific `connectionsBridge.providerOrigins`.
- Rolling from Steward 0.3.19 to 0.3.18 hides the bounded workspace-preparation
  explanations added by 0.3.19 and restores error logging during expected
  sandbox-deletion progress; it needs no database change.
- MCP-GW 0.6.0 documents no database rollback. Restoring the prior chart
  removes the new wrapper objects only if the deployment also removes their
  values. Preserve the OAuth database and credentials unless the provider's
  own removal procedure says otherwise.

For the **core, task-auth and browser-admin profiles in this BOM**, Jira and
governed execution remain absent. Regeneration changes the Steward chart and
image coordinates plus platform-version references; it does not add mcp-gw,
provider origins, Jira values, an agent catalog or Task execution.

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

session enforcement.

## Product changes

### Steward 0.3.18 and 0.3.19

0.3.18 adds catalog-defined provider tools and provider-specific Connections,
including governed Jira sign-in and read tools. Each Run receives only the
tools its Task approved. It also improves repository checkout discovery,
enforces per-run runtime and inference limits, records final inference spend,
and gives browser users stable explanations for failed or refused Runs.

0.3.19 returns the existing bounded workspace-preparation explanation through
the Run API and keeps expected sandbox-deletion progress out of error logs;
cleanup that stalls past the existing deadline remains an error.

### MCP-GW 0.6.0

MCP-GW adds the digest-pinned generic wrapper and the opt-in Jira provider.
Its recommended Jira preset exposes three read-only REST tools. Task tokens
are filtered to their exact provider actions, connection-status and
connection-start authority is provider-bound, and GitHub forwards only
validated fields. New or undecided live-provider tools remain hidden.

The chart also adds an opt-in GitHub MCP sidecar topology and an opt-in db-mcp
wrapper. This platform release does not enable either one.

## Upgrading from 2026.10.0-alpha.14

1. Read and satisfy the upgrade notes above. Back up the Steward database.
2. Regenerate from unchanged platform values. Review the new Steward chart and
   image pins and the platform tag references. No existing profile gains an
   mcp-gw release.
3. Copy or rebuild the changed Steward artifacts for a registry mirror or
   built-artifacts lock. Mirror the new MCP-GW artifacts only if the planned
   governed installation consumes them.
4. Apply with `helmfile --environment <env> --kube-context <context> sync`, or
   let Flux reconcile the regenerated objects. Wait for every old Steward
   apiserver, controller and Mint pod to leave before enabling new catalog
   fields.
5. If a separately maintained governed installation enables Jira, apply the
   complete MCP-GW values plus the temporary session setting above and the
   matching Steward provider origin. Otherwise leave Jira absent.

An alpha.14 built lock is refused because its Steward version and commit do
not match this BOM. Existing platform-values files still validate unchanged.

## What this repository verifies

The local and CI gates validate the BOM and schemas, resolve every pinned
digest, verify product attestations and signatures, regenerate every example,
render the pinned charts, exercise built mode and Helm hooks, and compare Flux
output with the generator. The cluster jobs install the core, task-auth and
browser-admin profiles on the tested Kubernetes versions and apply Steward's
migrations, including 0071.

This release does **not** install or exercise mcp-gw, Jira, governed Tasks,
provider origins, per-run inference limits, or the new wrapper topologies.
Those remain outside the implemented profiles. The mcp-gw pin is supply-chain
verified, not an end-to-end compatibility claim for an enabled provider.
